# runbook — Markdown手順書 自動実行フレームワーク

EXCEL作業手順書(説明・コマンド・コマンド正常性基準)を Markdown に置き換え、
一括実行 / 逐次インタラクティブ実行 / ステップ指定実行 を行うツール。

設計原則: **機械は実行と判定を担うが、継続の決定は常に人間が担う。**

- コマンドはこのマシン上の bash で実行する。ansible ad-hoc / ansible-playbook には
  専用ラッパー(```` ```ansible ```` / ```` ```playbook ```` フェンス)がある
- 正常性判定は「終了コード」と「出力への正規表現マッチ」を論理式で組み合わせて自動判定。
  NG時は**どの条件で落ちたかの判定内訳**を表示する
- **正常性基準を満たさなかった時点で必ず即中断**(exit code 1)。中断時はそのステップの
  失敗時ガイダンス(RB-ONFAIL)と切り戻しセクションの実行方法を案内する(自動では走らせない)
- `runbook check` で実行前に静的検証(書式・基準式・変数・インベントリ/プレイブックの
  パス存在)と展開後コマンドのプレビュー(`--preview`)ができる
- コマンドのない**手動ステップ**(目視確認・手作業・関係者連絡)も手順に書ける。
  実行時は説明を表示して作業者の完了確認を待ち、確認時刻を記録する
- 実行開始前にサマリー(対象ステップ・変数・インベントリ)の確認ゲートを挟み、
  **作業者名(必須)・確認者名(任意)** を記録する
- 実行ごとにエビデンスログ(人間可読ログ + JSON + 各ステップの生出力)を保存。
  `secrets: [DB_PASS]` と宣言した変数の値は**表示・ログのすべてからマスク**される
- 途中で中断した実行は `--start-from N` で再開できる(share_env の環境変数も復元)

## セットアップ

```bash
cd ~/wk_tool
.venv/bin/pip install -e .
# 以後 .venv/bin/runbook で実行(activate するなら runbook だけでよい)
```

## 使い方

```bash
runbook check 手順書.md              # 書式・基準式・変数・参照パスの検証のみ(実行しない)
runbook check --preview 手順書.md    # 検証に加えて展開後の実行コマンドを全文表示
runbook list  手順書.md              # ステップ一覧表示(切り戻しセクションも表示)
runbook renumber 手順書.md           # ## 見出しに実行順の連番(1. 2. ...)を付与/振り直し
runbook run   手順書.md              # 一括実行
runbook run -i 手順書.md             # 逐次インタラクティブ実行(各ステップ前に Enter/s/q)
runbook run --only 3 手順書.md       # ステップ3のみ実行
runbook run --only 1,3-5 手順書.md   # ステップ指定実行
runbook run --from 2 --to 4 手順書.md
runbook run --var HOST=web02 手順書.md   # 変数の上書き(複数指定可)
runbook run --start-from 5 手順書.md # ステップ5から最後まで再開(share_env なら環境変数も復元)
runbook run --rollback 手順書.md     # 切り戻しセクション(# RB-ROLLBACK)の実行
runbook run --operator 山田 --checker 田中 手順書.md  # 作業者・確認者を引数で指定
runbook run --yes 手順書.md          # 実行前サマリー確認をスキップ(非対話実行用)
runbook run --log-dir /path/to/logs 手順書.md
```

`run` は実行開始前に「実行前確認」(タイトル・対象ステップ・変数・使用インベントリの
サマリー)を表示し、`y` の入力を待つ。手順書やインベントリの取り違えに気付く最後の
ゲートであり、`--yes` を指定した場合のみスキップされる。続いて作業者名(未指定なら
入力を求める。非対話環境では `--operator` が必須)と確認者名(任意)を記録する。

終了コード: 0=正常終了(インタラクティブ実行での操作者スキップ含む) /
1=基準NG・タイムアウト・基準式評価エラーで中断 /
2=手順書やコマンドライン指定のエラー / 130=操作者中断(q または Ctrl-C、
実行前確認での中止、手動ステップの未完了中断を含む)

## 手順書フォーマット

````markdown
# ○○サーバ 定期メンテナンス手順

```runbook
vars:              # 変数の既定値(--var で上書き可)
  TARGET_HOST: web01
```

## 1. サービス状態の事前確認

### RB-DESCRIPTION
メンテナンス前にサービスが正常稼働していることを確認する。

### RB-CMD
```bash
systemctl status {{TARGET_HOST}}-nginx.service
```

### RB-EXPECTED
```
rc == 0 and out("active \(running\)") and not out("ERROR|FATAL")
```

### RB-LOCALDEF
```yaml
timeout: 300     # 秒。超過したらプロセスグループごと kill して NG 扱い
cwd: /var/tmp    # 実行ディレクトリ
```
````

- **`## 見出し` 1つ = 1ステップ**(記載順に番号が付く)。見出しの `1.` は表示用の連番
  (`runbook renumber` で自動付与、後述)。
- ステップ内のセクションは次の5種(大文字小文字は区別しない):

| セクション | 意味 | 省略 |
|---|---|---|
| `### RB-CMD` | 実行するコマンド | 可(省略すると**手動ステップ**になる。後述) |
| `### RB-EXPECTED` | 正常性基準(コマンドの合否判定式) | 可(省略時は `rc == 0`) |
| `### RB-DESCRIPTION` | 作業者向けの説明 | 可(手動ステップでは必須) |
| `### RB-LOCALDEF` | ステップ個別設定(timeout / cwd / ansible) | 可 |
| `### RB-ONFAIL` | 失敗して中断した瞬間に表示するガイダンス(自由記述) | 可 |

- `### RB-CMD` のコードフェンスが複数ある場合は連結して 1 つの bash スクリプトとして実行される(下記参照)。
- `{{VAR}}` はコマンドと正常性基準の中で置換される。未定義ならエラー。

### 手動ステップ(RB-CMD の省略)

`### RB-CMD` のないステップは**手動ステップ**になる。「VPNに接続する」「監視画面を
目視確認する」「顧客に開始連絡を入れる」のようなコマンド化できない作業を、コマンド
ステップと同じ手順書に並べて書くためのもので、これにより手順書全体を 1 つの .md に
統合できる(コマンドだけ runbook、それ以外は Excel という二重管理をなくす)。

````markdown
## 監視の一時停止を目視確認

### RB-DESCRIPTION
監視コンソールで対象ホストがメンテナンスモードになっていることを確認する。
````

- 実行時は RB-DESCRIPTION を表示し、作業者の完了確認(`y` の明示入力)を待つ。
  Enter の空打ちでは先に進まない。`q` で中断できる(exit code 130)
- 確認時刻と「誰が確認したか」(作業者名)が run.log と result.json に記録される
- 書き忘れとの区別のため、手動ステップには **RB-DESCRIPTION が必須**。
  また判定対象のコマンドがないため RB-EXPECTED / RB-LOCALDEF は書けない(パースエラー)。
  RB-ONFAIL は書ける
- 逐次インタラクティブ実行(`-i`)では完了確認プロンプトに `s`(スキップ)も選べる

### 失敗時ガイダンス(RB-ONFAIL)

任意の `### RB-ONFAIL` セクション(人間向けの自由記述)を書いておくと、そのステップが
NG・タイムアウト・基準式エラーで**中断した瞬間に表示される**。手順書作成者が知っている
「これが失敗したら次はこう動く」という知識を、一番必要な瞬間に作業者へ届けるための仕組み。
表示するだけで、自動修復や自動リトライは行わない(判断も実行も人間のまま)。

````markdown
### RB-CMD
```bash
systemctl restart app.service
```

### RB-ONFAIL
まず journalctl -u app.service で直近のエラーを確認。
ポート競合(Address already in use)なら手順書「app_port_conflict.md」へ。
15分で復旧しない場合は佐藤さん(内線1234)にエスカレーション。
````

表示された内容は run.log にも記録される。

### 切り戻しセクション(# RB-ROLLBACK)

レベル1見出し `# RB-ROLLBACK` を書くと、それ以降の `## ` ステップは**切り戻し
セクション**になる。通常の `runbook run` では実行されず、`runbook run --rollback` で
のみ実行される(ステップ番号も本編とは独立して 1 から振られる)。

````markdown
## 1. 設定の書き換え

### RB-CMD
```bash
deploy_new_config.sh
```

# RB-ROLLBACK

## 1. 設定を旧版に戻す

### RB-CMD
```bash
restore_old_config.sh
```
````

- 本編の実行が中断(基準NG・操作者中断)されたとき、切り戻しセクションがあれば
  「切り戻す場合は `runbook run --rollback 手順書.md`」と**案内が表示される。
  自動では絶対に実行しない**(切り戻すかどうかの判断は人間が行う)
- `--rollback` 実行時も通常実行と同じ扱い(実行前確認・作業者記録・失敗即中断・
  エビデンスログ)。ログディレクトリ名は `<手順書名>_rollback_<日時>` になる
- `--only` / `--from/--to` は切り戻しセクション内の番号を指す
- 切り戻しステップにも手動ステップ・RB-ONFAIL を書ける
- `# RB-ROLLBACK` は手順書に1つだけ。後ろにステップがないとパースエラー

### 作業者・確認者の記録

実行開始時に**作業者名(必須)と確認者名(任意)**を記録する。Excel 手順書の
作業者/確認者欄(ダブルチェック文化)に相当し、「いつ・誰が・何を・結果どうだったか」
の証跡が揃う。

- 対話実行では実行前に入力を求める。非対話実行(cron・CI での素振り実行など)では
  `--operator 名前` で指定する(なければエラー)。`--checker` は省略可
- 記録先: run.log(先頭行)と result.json(`procedure.operator` / `procedure.checker`)。
  手動ステップの完了確認にも作業者名が記録される

### 実行前サマリー確認

`runbook run` は実行開始前に、タイトル・実行対象ステップ一覧(手動ステップは明示)・
変数・**使用インベントリ**・切り戻しセクションの有無を表示し、`y` の入力を待つ。
CLI は一打で走るため Excel 時代より「手順書やインベントリの取り違え」が起きやすく、
その事故を仕様で防ぐためのゲート。`y` 以外の入力は中止(exit code 130)。

非対話実行では `--yes`(`-y`)でスキップできる。

### 共通設定(```runbook フェンス)

手順書の共通設定(`title` / `vars` / `share_env` / `ansible` / `secrets`)は、最初の `## ` より前の
前書きに置く **```runbook フェンス**(中身は YAML)で定義する。コードフェンスは標準の
Markdown 要素なので、どのプレビューでも設定内容が確実に表示される。

````markdown
# 手順書タイトル

```runbook
vars:
  TARGET_HOST: web01
share_env: true
```

## 1. 最初のステップ
...
````

- タイトルは本文の `# 見出し` で書けるので、設定が不要な手順書ではフェンス自体を省略できる
- ```runbook フェンスは前書き専用。ステップ内に置く(どのセクションでも)とパースエラー、
  前書きに複数あるのもエラー
- **frontmatter(ファイル先頭の `---`〜`---`)は runbook の設定としては使えない。**
  一般的な Markdown メタデータ(Obsidian のタグ等)として自由に書けるが、runbook は
  解釈せず読み飛ばす。ただし設定キー(`vars` / `share_env` / `ansible` / `secrets`)が frontmatter に
  書かれている場合は、「書いたのに効いていない」事故を防ぐためパースエラーにする

### シークレットマスキング(secrets)

パスワードやトークンを変数として使う場合、共通設定に `secrets:` として**変数名を明示宣言**
すると、その値が表示とログのすべて(ターミナル出力・run.log・result.json・
stepNN_stdout.txt / stderr.txt・`list` / `check --preview` の表示)から `*****` に
置換される。ログをテキスト保存して回覧する運用でも秘匿値が残らない。

````markdown
```runbook
vars:
  DB_PASS: SuperSecret99
secrets: [DB_PASS]
```
````

- プレフィックス等の暗黙の命名規則ではなく**明示宣言方式**。宣言した変数が未定義
  (vars にも `--var` にもない)ならパースエラー(書いたのに効かない事故防止)
- マスクされるのは「値」なので、コマンド出力に値がそのまま現れた場合
  (`echo` やエラーメッセージへの混入)もマスクされる
- **正常性判定は生の出力に対して行われる**。`out("{{DB_PASS}}")` のような基準式も
  正しく判定され、表示・記録時のみマスクされる
- 値は `--var DB_PASS=...` で実行時に渡すこともできる(手順書に値を書かない運用)
- 注意: `share_env: true` と併用する場合、`export` した値は次ステップへの引き継ぎ用
  ファイル shared_env.sh に**平文で残る**(実行に必要な状態ファイルのためマスク不可。
  実行前確認にも注意が表示される)。ログディレクトリの保管・削除ルールに注意すること

### 複数コードフェンスの連結

フェンスの間に説明文を挟んで書ける。説明文は捨てられ、フェンスの中身だけが上から順に
連結されて **1 回の bash 起動でまとめて実行**される。

````markdown
### RB-CMD
まず作業ファイルを作る:
```bash
WORKFILE=/tmp/work.txt
echo "data" > "$WORKFILE"
```
次に内容を確認する:
```bash
cat "$WORKFILE"
```
````

上記は次のスクリプトを 1 回実行するのと同じ:

```bash
WORKFILE=/tmp/work.txt
echo "data" > "$WORKFILE"
cat "$WORKFILE"     # 同一プロセスなので前のフェンスの変数がそのまま使える
```

- 連結できるのは同種のフェンスのみ。ansible / playbook フェンスと他の言語のフェンスを
  同じ RB-CMD に混在させるとパースエラー(同種のフェンス同士なら複数書ける)
- 連結は改行区切り(`;` 相当)。各行は**前の行の成否に関係なく**順に実行される
- `rc` は**最後のコマンド**の終了コード。途中の失敗は最後が成功すると rc=0 に隠れるため、
  途中の失敗で即失敗にしたい場合は先頭フェンスに `set -e` を書く(連結後の全体に効く)
- 出力・正常性判定は全フェンスまとめてステップ単位で行われる

### ステップの区切りルール(見出しの扱い)

1ステップ = **`## ` 見出しの行から、次の `## ` 見出しの直前(またはファイル末尾)まで**。

| 見出し | 意味 |
|---|---|
| `# `(レベル1) | 手順書タイトル。ステップにはならない(共通設定に `title:` があればそちらが優先)。`# RB-ROLLBACK` だけは特別で、切り戻しセクションの開始区切りになる |
| `## `(レベル2) | **ステップの開始**。見出しテキストがステップ名になり、番号は出現順に 1 から自動採番される(`--only` や `--from/--to` はこの番号を指す)。切り戻しセクション内は独立して 1 から採番 |
| `### `(レベル3) | ステップ内の区画。`RB-CMD` / `RB-EXPECTED` / `RB-DESCRIPTION` / `RB-LOCALDEF` / `RB-ONFAIL` の5種のみ有効で、それ以外の名前はパースエラー |

### 見出しの連番(Markdownプレビュー用)

`runbook renumber 手順書.md` を実行すると、`## ` 見出しに実行順の連番
(`## 1. 事前確認` の形式)が付与/振り直しされ、一般的な Markdown プレビューでも
ステップが番号付きで表示される。切り戻しセクション(`# RB-ROLLBACK` 以降)は
独立して 1 から振り直される。

- パース時、見出し先頭の `1.` `2:` 等はステップ名から除去される(実行時表示や
  `run.log` が「ステップ 1/6: 1. …」のように二重にならない)。番号の有無は実行に影響しない
- ステップ番号は常に**記載順で自動採番**される。見出しに書かれた番号が実際の順序と
  ズレている場合(ステップの挿入・削除後など)は `runbook check` が警告する →
  `renumber` で振り直す
- `100台対応` のような「番号でない先頭数字」(数字+区切り記号 `.` `．` `:` `：` の形式で
  ないもの)はステップ名としてそのまま保持される。区切り記号の後の空白は不要なので、
  `## 3:00までに完了確認` のような見出しは先頭の `3:` が連番と解釈されてステップ名が
  「00までに完了確認」になる点に注意(時刻を見出しに書く場合は `## 03時までに…` 等にする)

注意点:

- **コードフェンス(``` )の内側にある `##` / `###` 行は見出しとして扱わない。** ヒアドキュメントや
  出力例にステップ見出しと同じ書式の行が含まれていても誤分割されず、bash の
  `### コメント ###` のような行もそのまま書ける。
- 逆に、フェンスの外で行頭に `## ` を書くと必ず新しいステップの開始と解釈される。
  説明文の途中で `##` を行頭に書かないこと。
- 区切りの認識が意図どおりかは `runbook list 手順書.md`(ステップ番号・名前の一覧)と
  `runbook check 手順書.md` で確認できる。

### 要素の順序ルール

順序が決まっているもの:

- ```runbook フェンス(共通設定)と `# タイトル` は最初の `## ` より前(前書き)に書く
- frontmatter(runbook は解釈しない)は**ファイル先頭**にある場合のみ読み飛ばされる
- `## ` ステップは**記載順 = 実行順 = ステップ番号**(`--only` 等はこの番号を指す)
- `# RB-ROLLBACK`(切り戻しセクション)は本編ステップの**後**に書く(以降が切り戻し扱い)
- `### RB-CMD` 内の複数フェンスは上から順に連結して実行される
- ansible フェンスの行内指定(`ansible ... -i ...`)は必ず**1行目**
- playbook フェンスの各行は上から順に実行される

順序が自由なもの:

- 共通設定内のキー(`title` / `vars` / `share_env` / `ansible` / `secrets`)
- ステップ内の `### RB-DESCRIPTION` / `### RB-CMD` / `### RB-EXPECTED` / `### RB-LOCALDEF` /
  `### RB-ONFAIL`(順不同。読みやすさのため RB-DESCRIPTION → RB-CMD → RB-EXPECTED →
  RB-LOCALDEF → RB-ONFAIL の順を推奨)
- `### RB-LOCALDEF` 内の YAML キー

注意すべき境界挙動:

- 同名セクションを重複して書くと**後勝ち**(エラーにならず前のものは捨てられる)
- 最初の `## ` より前の本文テキストは実行対象にならない(前書きとして安全に使える。
  ただし ```runbook フェンスだけは共通設定として解釈される)
- `### RB-EXPECTED` / `### RB-LOCALDEF` はフェンスが複数あっても**最初の1つだけ**使われる
  (連結されるのはコマンドのみ)

## 正常性基準の書き方

Python 風の論理式。安全のため使える要素は以下に限定される(任意コード実行は不可)。

| 要素 | 意味 |
|---|---|
| `rc` / `exit_code` | コマンドの終了コード |
| `stdout` / `stderr` | 出力全文(文字列)。`"failed=0" in stdout` のように使う |
| `out("正規表現")` | 標準出力に正規表現がマッチすれば True |
| `err("正規表現")` | 標準エラーにマッチすれば True |
| `match("正規表現")` | 標準出力+標準エラーを対象に検索 |
| `and` `or` `not` `( )` | 論理演算 |
| `==` `!=` `<` `<=` `>` `>=` `in` `not in` | 比較 |

例:

```
rc == 0
rc == 0 and out("active \(running\)") and not out("ERROR|WARN")
(rc == 0 or rc == 2) and "failed=0" in stdout and "unreachable=0" in stdout
```

正規表現内で `(` `)` などをリテラルとして使う場合は `\(` のようにエスケープする。

### 判定内訳(NG時の詳細診断)

基準式が `and` で複数の条件を結合している場合、NG で中断したときに**どの条件で
落ちたか**の内訳が表示される(run.log と result.json の `criteria_breakdown` にも記録):

```
  ├ 判定内訳:
  │   [OK] rc == 0
  │   [OK] out("active")
  │   [NG] not out("ERROR|FATAL")
  └ 結果: ✘ Failed (rc=0, 0.01s)
```

- 分解されるのは `and` の結合のみ。`(rc == 0 or rc == 2)` のような or のまとまりや
  `not 〜` は、作成者が書いた1つの判断単位としてまとめて評価される
- 条件が1つだけの基準式では内訳は表示されない(基準式そのものと同じ情報のため)

## ansible ad-hoc コマンド(shellモジュール)ラッパー

コードフェンスの言語を `ansible` にすると、その内容をリモートで実行するコマンドとみなし、
`ansible <target> -i <inventory> -m shell -a '<コマンド>'` に組み立てて実行する。
リモートコマンドは自動でクォートされるので、`"` や `&&` を含んでいてもそのまま書ける。

````markdown
## 全webサーバの稼働確認(行内指定スタイル)

### RB-CMD
```ansible
ansible webservers -i inventories/web.ini
uptime
```

### RB-EXPECTED
```
rc == 0 and out("CHANGED|SUCCESS") and not out("UNREACHABLE|FAILED")
```

## DBサーバの確認(RB-LOCALDEF スタイル)

### RB-CMD
```ansible
df -h /var/lib/mysql
```

### RB-LOCALDEF
```yaml
ansible:
  inventory: inventories/db.ini  # このステップで使うインベントリ
  target: db01                   # ホストグループまたはホスト名
  extra_args: --become           # ansible コマンドに追加する引数(そのまま挿入)
```
````

- **inventory は毎回ステップごとに指定する(行内指定 または ステップ設定)。**
  共通設定(```runbook フェンス)に inventory を書くとパースエラーになる。
  デフォルトのインベントリを許すと、指定漏れがエラーにならず「意図しない環境」で
  実行される事故につながるため、意図的にこの仕様としている。
- target は ad-hoc では必須(行内指定・ステップ設定・共通既定のいずれかで指定)。
  共通設定の `ansible:` に既定値を書ける(インベントリ内での絞り込みのため)。
  extra_args / host_matrix も同様に共通既定値を書ける。
- inventory / target / extra_args には `{{VAR}}`(runbook のテキスト置換)が使える。

### ad-hoc の行内指定(フェンス1行目の ansible 行)

フェンスの**1行目を `ansible ` で始める**と、その行がターミナルで打つのと同じ
起動指定(ターゲット・`-i`・オプション)としてそのまま使われ、**共通設定/ステップ設定の
target・inventory は使われない**。2行目以降がリモートコマンドになる。

````markdown
### RB-CMD
```ansible
ansible dbservers -i inventories/db.ini -e MODE=quick
df -h /var/lib/mysql
```
````

- 起動指定行はコントローラ側の値なので `{{VAR}}` のテキスト置換が効く
  (例: `ansible db -i inventories/{{ENV}}/db.ini`)
- 行内に書いた `-e` は自動付与の変数 JSON より後ろに並ぶため**優先**される
- 起動指定行の後にリモートコマンドがないとパースエラー
- リモートコマンド自体が `ansible ` で始まる(リモートで ansible を実行する)場合は
  この記法と衝突するため、1行目に起動指定を書くか、リモート側でフルパス
  (`/usr/bin/ansible ...`)を使うこと
- 実行例は [samples/sample_ansible.md](samples/sample_ansible.md) と、自ホストを6つの擬似ホスト
  (web01-03/db01-02/mon01, `ansible_connection=local`)に見立てて実 ansible で動かせる
  [samples/local_test/](samples/local_test/) を参照。

### ansible-playbook ラッパー

コードフェンスの言語を `playbook`(または `ansible-playbook`)にする。フェンスの各行は
**「ansible-playbook に渡す引数列」そのもの**で、プレイブックのパスに続けて
`-e KEY=VALUE` や `--check` などのオプションをそのまま書ける。
`ansible-playbook -i <inventory> [-l <target>] -e '{変数JSON}' [extra_args] <行の内容>`
に組み立てて実行される。

````markdown
## アプリのデプロイ

### RB-CMD
```playbook
-i inventories/web.ini playbooks/deploy.yml -e APP_VERSION=1.2.3
```

### RB-LOCALDEF
```yaml
ansible:
  target: webservers        # 指定すると -l(limit)で対象を絞る。省略可
```

### RB-EXPECTED
```
rc == 0 and not out("failed=[1-9]|unreachable=[1-9]")
```
````

ad-hoc との違い・共通点:

- **行内に `-i <インベントリ>`(または `--inventory`)を書ける**。行に `-i` がある場合、
  設定側の inventory は付与されない(行が優先。ansible は複数の `-i` を「結合」して
  しまうため二重付与はしない)。処理系統ごとにインベントリを切り替える運用では
  行ごとに `-i` を書き分ければよい:

  ```playbook
  -i inventories/web.ini deploy_web.yml
  -i inventories/db.ini backup_db.yml -e MODE=full
  ```

- **インベントリは毎回指定必須**(ad-hoc と同じ方針)。行内の `-i` か、行内に `-i` が
  ない行にはステップ設定の `ansible: inventory` が適用される。どちらにもない行は
  パースエラー。共通設定への指定は不可。
  **target は省略可**で、指定時のみ `-l` として適用される
  (対象ホストはプレイブック側の `hosts:` が基本)
- 手順書の変数は ad-hoc と同様 `-e` で自動的に渡るので、**プレイブック内の jinja2 から
  `{{ VAR }}` でそのまま参照できる**。行内に書いた `-e` は自動付与分より後ろに並ぶため、
  **同名変数は行内に書いた値が優先**される(実行ごとに変えたい値の上書きに使える)
- 行の内容はコントローラ側の値なので `{{VAR}}` のテキスト置換が効く
  (例: `playbooks/{{ENV}}/deploy.yml`)。パスに空白を含む場合は自分でクォートすること
- 複数行書くと 1 行ずつ `ansible-playbook` が起動され、`&&` 連結なので
  **1 つでも失敗したら以降の行は実行されない**
- `#` で始まる行は無視される
- `host_matrix: true` は PLAY RECAP(`web01 : ok=2 ... failed=0`)を解析して
  ホスト別マトリックスを表示する
- 判定パターンの定番: `rc == 0 and not out("failed=[1-9]|unreachable=[1-9]")`

### ansible フェンス内の変数と jinja2

**ansible フェンスの中は、すべて ansible(jinja2)の世界。** runbook はフェンスの中身に
テキスト置換を行わず、手順書の変数を extra-vars(`-e '{"VAR": "値", ...}'`)として
自動的に渡す。そのため:

- 手順書の変数は bash フェンスと同じ `{{VAR}}` 記法でそのまま使える(解決するのは ansible)
- `{{ inventory_hostname }}` や `{{ hostvars[...] }}` などの jinja2 記法も
  エスケープ不要でそのまま書ける

```ansible
echo "{{CHECK_LABEL}}: {{ inventory_hostname }} は正常です"
```

変数名をタイポした場合は ansible が `'CHEK_LABEL' is undefined` のようなエラーで
rc≠0 を返し、NG・即中断となる(bash フェンスの `{{VAR}}` はパース時に検出されるのに対し、
ansible フェンスは実行時検出になる点だけ注意)。

### ホスト別結果マトリックス(host_matrix)

`ansible:` 設定(共通設定またはステップの設定)に `host_matrix: true` を付けると、
ansible ステップの実行後に**列=ホスト名、値=成功/失敗マーク**のマトリックスを表示する。
共通設定に書けば手順書全体の既定になる(inventory と違い表示専用の設定なので共通指定可)。

```yaml
ansible:
  host_matrix: true    # ステップ設定で false にして個別に無効化も可
```

ステップごとの表示(マークはレイアウト崩れ防止のため半角英数のみ):

```
ホスト別結果:
  db01  db02  mon01  web01  web02  web03
   O     O      O      O      X      !
O=成功  X=失敗  !=到達不能  -=対象外
```

host_matrix 有効なステップが2つ以上あると、実行終了時に行=ステップの集約マトリックスも表示する:

```
=== ホスト別結果マトリックス ===
ステップ                            db01  db02  mon01  web01  web02  web03
1: 全6ホストの疎通確認               O     O      O      O      O      O
2: webservers グループのみ負荷確認   -     -      -      O      O      O
```

ホスト別結果は表示に関わらず ansible ステップの `result.json` に `host_results`
(`ok` / `failed` / `unreachable`)として常に記録される。

### ansible ad-hoc の判定パターン(ansible core 2.21 実機確認済み)

| 状況 | ansible の rc | 出力の特徴 |
|---|---|---|
| 全ホスト成功 | 0 | `web01 \| CHANGED \| rc=0 >>` |
| いずれかのホストでコマンド失敗 | 2 | `db01 \| FAILED \| rc=1 >>` |
| いずれかのホストに到達不能 | 4 | `badhost \| UNREACHABLE! => {` |

判定は ansible コマンド自体の終了コードと出力に対して行う。1台でも失敗すると rc≠0 に
なるため既定の `rc == 0` でも機能するが、次の形を定番とするのが確実:

```
rc == 0 and not out("UNREACHABLE|FAILED")
```

特定ホストの応答を確認したい場合(`|` は正規表現の特殊文字なので `\|` とする):

```
rc == 0 and out("web01 \| CHANGED") and not out("UNREACHABLE|FAILED")
```

なお基準式の文字列内では `\|` や `\d` などのバックスラッシュをそのまま書ける
(Python のエスケープ警告は評価器側で処理している)。

## ステップ間の環境変数引き継ぎ(share_env)

通常、各ステップは独立した bash プロセスで実行されるため `export` は次のステップに
残らない。共通設定に `share_env: true` を書くと、各ステップの実行前に共有ファイルを
`source`、実行後に `export -p` で保存する動作になり、`export` した変数が後続ステップに
引き継がれる。「ステップ1でトークンを取得してステップ2で使う」用途向け。

````markdown
```runbook
share_env: true
```

## トークンを取得する

### RB-CMD
```bash
export API_TOKEN=$(curl -s https://api.example.com/auth | jq -r .token)
```

## 取得したトークンを使う

### RB-CMD
```bash
curl -s -H "Authorization: Bearer $API_TOKEN" https://api.example.com/status
```
````

注意点:

- 共有ファイルはログディレクトリ内の `shared_env.sh` に保存される。トークン等の秘匿情報が
  平文で残るため、ログディレクトリの保管・削除ルールに注意すること。
- ステップのコマンド内で `exit` すると、その時点で終了するため環境変数は保存されない。
- ステップの終了コードは(保存処理ではなく)コマンド本体の最後の終了コードが使われる。

## 途中からの再開(--start-from)

終盤のステップで NG になった手順書を最初からやり直さなくて済むよう、
`--start-from N` で**ステップ N から最後まで**を再開実行できる。

```bash
runbook run 手順書.md                    # ステップ12でNG・中断したとする
runbook run --start-from 12 手順書.md    # 原因を解消してから12以降を再開
```

`--from N`(単なる範囲指定)との違いは環境変数の扱い:

- `share_env: true` の手順書では、**直近実行のログディレクトリから shared_env.sh を
  探して新しい実行に復元**する。「ステップ1で取得したトークンをステップ12が使う」
  ような依存があっても再開できる
- 復元元が見つからない場合はエラーで停止する(前段の環境変数がないまま走る事故を
  防ぐため)。環境変数なしで実行してよいと判断した場合は `--from N` を使う
- `share_env` を使っていない手順書では `--from N --to 最後` と同じ動作
- 復元元は実行前確認と run.log / result.json(`resumed_env_from`)に記録される
- `--only` / `--from` / `--to` とは併用不可。`--rollback` とは併用可
  (切り戻しセクション内のステップ番号・切り戻し実行のログが対象になる)

再開はあくまで**人間が原因を確認・解消した後に指示する**もので、自動リトライではない。

## 事前検証(runbook check)

`runbook check` は実行せずに手順書を検証する。本番の途中で初めて気付く事故を
実行前に潰すためのもので、作業直前に**実行するのと同じディレクトリ・同じ引数
(`--var` 含む)で**流しておくことを推奨する。

エラー(NG、exit code 1):

- 書式エラー(セクション名・フェンス・共通設定などのパースエラー全般)
- 変数の未定義(`{{VAR}}` が vars / --var のどちらにもない)
- 正常性基準式の構文エラー・使用不可の要素・不正な正規表現

警告(表示のみ、exit code 0):

- 見出しの連番と実際の順序の不一致(`renumber` で振り直せる)
- **インベントリファイルが見つからない**(ansible 系ステップの参照先を実際に確認)
- **プレイブックファイルが見つからない**(playbook 行内の `*.yml` / `*.yaml` を確認)
- RB-LOCALDEF の `cwd` が存在しない

パス類をエラーでなく警告とするのは、check したディレクトリと実行するディレクトリが
違う場合に誤検知になり得るため(カンマを含むインベントリ指定は ansible の
インラインホストリストとみなしチェックしない)。

`--preview` を付けると、検証に加えて**変数展開・ansible コマンド組み立て後の
実行コマンド全文**がステップごとに表示される(切り戻しセクション含む)。実際に
何が実行されるかを目で確認してから本番に臨める。

```bash
runbook check --preview --var HOST=web02 手順書.md
```

## 実行ログ(エビデンス)

実行 1 回ごとに `logs/<手順書名>_<日時>/` が作られる(`--rollback` 実行時は
`logs/<手順書名>_rollback_<日時>/`。同一秒内の連続実行では `_2` 等の連番が付き、
証跡が混ざることはない):

| ファイル | 内容 |
|---|---|
| `run.log` | タイムスタンプ付きの実行経過と判定(人間可読)。作業者・確認者、手動ステップの確認時刻、表示した RB-ONFAIL・切り戻し案内も残る |
| `result.json` | 全ステップの結果サマリ(機械可読)。`procedure.operator` / `procedure.checker` / `procedure.rollback`、NG時は `criteria_breakdown`(判定内訳)を含む |
| `stepNN_stdout.txt` / `stepNN_stderr.txt` | 各ステップの生出力(手動ステップは空ファイル) |

- `secrets:` 宣言した変数の値は上記すべてから `*****` にマスクされる
  (shared_env.sh のみ実行に必要なため平文。シークレットマスキングの節を参照)
- 実行前サマリー確認で中止した場合はログディレクトリ自体が作られない
  (実行が始まっていないため)。

## 既知の制約

- コマンド実行中の対話入力には対応しない(コマンドの stdin は閉じる)。パスワード等が
  必要な場合は `ansible-vault` のパスワードファイルや SSH 鍵など非対話手段を使うこと。
  (runbook 自身のプロンプト — 実行前確認・作業者入力・手動ステップの完了確認 — は
  この制約とは別で、端末から入力する)
- 非対話環境(cron・CI での素振り実行など)では `--yes` と `--operator` を指定する。
  手動ステップを含む手順書は完了確認ができないため非対話環境では実行できない
  (確認プロンプトで EOF となり中断する)。
- 実行先はローカルのみ。リモートは ansible / ssh コマンドを手順書に書くことで対応。
