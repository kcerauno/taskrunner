# `runbook run` 出力の可読性改善案(情報量を減らさない前提)

> **実装状況(2026-07-30)**: 案R1・R2・R3・R4・R5・R6・R9 を実装済み。
> 案R7(`--tail-lines`)と案R8(経過表示)は未実装。
> 実測効果: feature_test.md(6ステップ)の出力が **232行 → 203行**。
> リザルト一覧表(8行)を新設した上での削減なので、既存部分は実質37行圧縮。
> 凡例の重複は6回→2回。テストは 146件 → 168件(+22)。
>
> 実装で判明した追加事項(当初案になかったもの):
> - 判定内訳の `→` 揃えは `len()` では崩れる。全角文字が1幅として数えられるため
>   `rich.cells.cell_len` で表示幅を使う必要があった。
> - 表の上下の空行は `pad_edge=False` では消えず、`show_edge=False` が必要だった。
> - 案R6 の「実際の出力」にはコマンド出力の本文が入るため、**マスク適用が必須**。
>   シークレットが証跡に漏れないことをテストで固定した。
> - 案R4 の「開始/終了を1行に統合」は**採用しなかった**。`開始` 行は実行中の
>   ライブフィードバック(長時間ステップで生きていることを示す)を兼ねており、
>   完了後にまとめて出すと機能が落ちる。代わりに終了時刻を `結果` 行へ移して1行削減した。


対象: [runbook/cli.py](../runbook/cli.py) `cmd_run` (L340-564), [runbook/render.py](../runbook/render.py)
関連: [output_readability_proposals.md](output_readability_proposals.md)(`list` / `check --preview` 向け)

## 検証方法

実際に実行して出力を採取した(推測ではない)。

```
COLUMNS=100 .venv/bin/runbook run samples/local_test/feature_test.md -y \
  --operator c --checker c --log-dir <scratchpad>/logs
```

- 成功系: `samples/local_test/feature_test.md`(6ステップ / ansible ad-hoc・playbook・bash 混在)
  → **総出力 232 行**
- 失敗系: 判定内訳と RB-ONFAIL を出すための手順書を作成して実行

## 現状の問題(実測)

### 問題1 ★最大: 最終サマリーが「どのステップが落ちたか」を言わない

失敗時の末尾は実測でこれだけ。

```
・ 実行結果: 実行中断
  └ ログ保存先: .../logs4/fail_test_20260730_204030
```

ステップ番号もステップ名も、何ステップ成功して何ステップが未実行かも書かれていない。
232行スクロールして遡らないと「どこで落ちたか」が分からない。
`art.records` には rc・所要時間・status が全て入っている([cli.py:538](../runbook/cli.py#L538)
で `art.records` を参照済み)ので、出せる情報を出していないだけ。

失敗即中断の設計上、**中断後のステップは出力に一切現れない**。
「6ステップ中2番で落ちた → 3〜6は未実行」を読み手が引き算で推測している。

### 問題2: ホスト別結果マトリックスが1ステップ5行を占め、うち2行が空白

実測(ステップ1の出力):

```
  ├ ホスト別結果:
  │                                                     
  │        db01   db02   mon01   web01   web02   web03  
  │    ──────────────────────────────────────────────── 
  │         O      O       O       O       O       O    
  │                                                     
  │   O=成功  X=失敗  !=到達不能  -=対象外
```

`box.SIMPLE` + `pad_edge=True`([render.py:91-96](../runbook/render.py#L91-L96))が
上下に空行を生む。データは実質1行なのに5行使っている。

### 問題3: 凡例が毎ステップ繰り返される

`O=成功 X=失敗 !=到達不能 -=対象外` が ansible ステップごとに出力され、
実測で **6回**(各ステップ5回 + 最終マトリックス1回)。
[cli.py:497](../runbook/cli.py#L497) で毎回 `_MATRIX_LEGEND` を出している。

### 問題4: 終了タイムスタンプがほぼ純粋な冗長

```
  ├ 開始: 2026-07-30 20:39:22
  ├ 終了: 2026-07-30 20:39:23
  └ 結果: ✓ Completed (rc=0, 1.124s)
```

日付は `実行開始` ヘッダにも出ており、全ステップで同一。所要時間は `結果` 行に既にある。
実測で `├ 終了:` 行が6回。

**問題2〜4の合計**: 232行中、マトリックス余白10行 + 凡例の2回目以降5行 + 終了行6行 ≒ **21行(約9%)が情報を持たない行**。

### 問題5: コマンド出力が全て同じ視覚的重みで流れる

失敗系の実測:

```
  │   hello world          ← 判定に関係する行
  │   noise line 1
  │   noise line 2
   (…12行)
```

`echo` は stderr のみ赤、それ以外は無装飾([cli.py:439-441](../runbook/cli.py#L439-L441))。
ansible の `web03 | CHANGED | rc=0 >>` というホスト区切り行も、その中身と同じ重みで表示される。
出力が長いほど構造(どこからどのホストの結果か)が埋もれる。

### 問題6: 判定内訳が「なぜNGか」まで届いていない

実測:

```
  ├ 判定内訳:
  │   [OK] rc == 0
  │   [OK] out("hello")
  │   [NG] out("NOT_PRESENT")
  │   [NG] not out("noise")
```

どの項が落ちたかは分かるが、**出力側の実態が分からない**。
特に `not out("noise")` は「何行が・どの行がマッチしたのか」が知りたい情報であり、
それを出さないと結局スクロールして出力を目で探す作業に戻る。

### 問題7(不具合): RB-ONFAIL をフェンス内に書くと黙って捨てられる

検証中に実際に踏んだ。`### RB-ONFAIL` の内容をコードフェンスで囲んで書いたところ、
**失敗時ガイダンスが一切表示されなかった**。原因は
[parser.py:164-174](../runbook/parser.py#L164-L174) の `_plain_text` がフェンス**外**の
行のみを拾う実装のため。

```python
def _plain_text(body_lines):      # フェンス内は捨てられる
    ...
    if re.match(r"^\s*```", line):
        in_fence = not in_fence
        continue
    if not in_fence:
        out.append(line)
```

仕様([02_runbook_format.md:111](external_spec/02_runbook_format.md#L111))は「自由記述」で、
サンプルもフェンスなしなので**書き方としては誤り**。しかし:

- `runbook check` は警告を出さない(検証したが無警告で OK になった)
- 気付けるのは「失敗したのにガイダンスが出ない」瞬間だけ = 最も困っている時

`RB-ONFAIL` / `RB-DESCRIPTION` のセクションがあるのに `_plain_text` の結果が空になる場合は
`check` で警告すべき。これは可読性ではなく正しさの問題。

## 改善案

### 案R1 ★最優先: 最終サマリーにステップ別リザルト一覧を出す

問題1の解消。`art.records` にある情報を出すだけで、追加の計測は不要。

```
・ 実行結果: 実行中断 — ステップ 2「基準を満たさず落ちるステップ」で失敗

   No.  ステップ                        結果      rc   所要
  ────────────────────────────────────────────────────────────
    1   正常に終わるステップ            ✓ 完了     0   0.004s
    2   基準を満たさず落ちるステップ    ✘ 失敗     0   0.009s   ← 中断
    3   到達しないステップ              - 未実行    -        -
  └ ログ保存先: .../logs4/fail_test_20260730_204030
```

- 1行目で「どこで落ちたか」が即分かる(現状は不明)
- `- 未実行` を明示し、中断で飛ばされたステップを引き算で推測させない
- スキップ(`→ スキップ`)も同じ表に並ぶ。現状 `n_skipped`
  ([cli.py:551](../runbook/cli.py#L551))は件数だけでどのステップか分からない
- 成功時も同じ表を出す(全ステップの所要時間が一覧でき、遅いステップが見える)

情報は増えるだけで、減るものはない。**単独で最も効果が大きい。**

### 案R2: 単一ステップのホスト別結果はインライン1行にする

問題2の解消。マトリックス表(2次元)は最終集約でこそ意味があり、
1ステップ分(1行)ではテーブルの枠が情報量に見合わない。

実測した3案の比較:

```
現状(5行):
  │                                                     
  │        db01   db02   mon01   web01   web02   web03  
  │    ──────────────────────────────────────────────── 
  │         O      O       O       O       O       O    
  │                                                     

案a: box=None, pad_edge=False(2行):
  │     db01  db02  mon01  web01  web02  web03
  │      O     O      O      O      O      O  

案b: インライン(1行) ★推奨:
  ├ ホスト別結果: db01=O db02=O mon01=O web01=O web02=O web03=O
```

案bの形式は `host_results_logline`([render.py:113-114](../runbook/render.py#L113-L114))として
既に存在し、`run.log` で使われている。**コンソールとログの表記が揃う副次効果もある。**
ホスト数が多く1行に収まらない場合のみ案aの表にフォールバックする。

最終集約マトリックス([cli.py:537-547](../runbook/cli.py#L537-L547))は2次元に意味があるので
表のまま維持し、`pad_edge=False` だけ適用する。

### 案R3: 凡例は初回のみ + 最終マトリックスに出す

問題3の解消。6回 → 2回。出力から消えるわけではないので情報は失われない。
実装は `cmd_run` にフラグを1つ持つだけ([cli.py:497](../runbook/cli.py#L497))。

案R2(インライン化)を採ると `O`/`X`/`!` の意味は `db01=O` の形で文脈から読めるため、
凡例の重要度自体が下がる。

### 案R4: 開始/終了を1行に統合する

問題4の解消。

```
現状(2行 + 結果行):        案(1行 + 結果行):
  ├ 開始: 2026-07-30 20:39:22    ├ 実行: 20:39:22 → 20:39:23 (1.124s)
  ├ 終了: 2026-07-30 20:39:23    └ 結果: ✓ Completed (rc=0)
  └ 結果: ✓ Completed (rc=0, 1.124s)
```

日付は `実行開始` ヘッダにあるので時刻のみで足りる。
日付が変わる長時間実行(日跨ぎ)のみ日付を併記する条件分岐を入れる。

### 案R5: 出力行のうち「構造を示す行」を強調する

問題5の解消。文字は一切削らず、スタイルのみ変える。

- ansible のホスト区切り行(`^\S+ \| (CHANGED|SUCCESS|OK) \| rc=\d+ >>`)→ 通常輝度またはシアン
- 同じく `FAILED` / `UNREACHABLE` を含むホスト行 → 赤/黄(現状は rc が0なら無装飾で流れる)
- playbook の `PLAY [...]` / `TASK [...]` / `PLAY RECAP` → 見出しとして強調
- それ以外の本文 → やや dim

これにより「長い出力の中でどこがホストの切り替わりか」が一目で分かる。
実装は [cli.py:439-441](../runbook/cli.py#L439-L441) の `echo` に正規表現分岐を足す。
`markup=False` は維持する(出力内の `[...]` を Rich マークアップと誤解釈させないため。
playbook の `TASK [名前]` があるので**これは必須**)。

### 案R6 ★診断価値が高い: 判定内訳に「実際どうだったか」を添える

問題6の解消。**情報を増やす**提案。

```
  ├ 判定内訳:
  │   [OK] rc == 0                    (実際: rc=0)
  │   [NG] out("NOT_PRESENT")         → stdout/stderr にマッチなし
  │   [NG] not out("noise")           → 12行がマッチ (初出 L2: "noise line 1")
```

`criteria.diagnose` は既に項ごとに評価している([cli.py:511](../runbook/cli.py#L511))ので、
同じ場所でマッチ件数と初出行を取れる。
これがあると「出力を目でスクロールして探す」作業がほぼ不要になる。

### 案R7: 長い出力の折りたたみ(opt-in)

`--tail-lines N` を追加し、コンソールには末尾N行のみ表示する。

**情報は失われない**: 全文は常に `stepNN_stdout.txt` / `stepNN_stderr.txt` に
逐次書き込まれている([cli.py:437-447](../runbook/cli.py#L437-L447))。
省略した場合は必ず参照先を出す。

```
  │   (… 全120行。先頭100行を省略。全文: step04_stdout.txt)
  │   web03 | CHANGED | rc=0 >>
```

既定はオフ(現状の全行表示のまま)。数百ホストの ansible 実行で初めて必要になる機能なので、
既定を変えて既存の運用を壊さないこと。

### 案R8: 長時間ステップの経過表示

出力を出さないコマンドが数分続くと、生きているのか止まっているのか分からない。
Rich の `Status`(スピナー + 経過秒)を出力が無い間だけ表示する。

**注意**: `soft_wrap=True` の設計意図(tee でテキスト保存しても行が崩れない、
[render.py:16-17](../runbook/render.py#L16-L17))と衝突する。
スピナーは再描画するので、非TTY(パイプ・tee)では無効化する条件分岐が必須。

### 案R9(不具合修正): 空の RB-ONFAIL / RB-DESCRIPTION を `check` で警告する

問題7の解消。セクション見出しはあるが `_plain_text` の結果が空文字なら警告する。

```
警告 ステップ2「...」: RB-ONFAIL の内容が空です
     (コードフェンス内に書かれている可能性があります。RB-ONFAIL はフェンスなしで記述します)
```

可読性ではなく正しさの改善だが、**失敗した瞬間に出るべきガイダンスが黙って消える**という
影響の大きさから、優先度は高い。

## 推奨する適用順

| 順 | 案 | 効果 | 変更規模 |
|---|---|---|---|
| 1 | 案R1 ステップ別リザルト一覧 | 「どこで落ちたか」が即分かる。単独で最大の効果 | 小(既存 `art.records` を出すだけ) |
| 2 | 案R9 空セクションの警告 | ガイダンスの消失を防ぐ(不具合) | 小 |
| 3 | 案R6 判定内訳にマッチ実態 | 失敗調査でスクロールが不要になる | 中(`criteria.diagnose` 拡張) |
| 4 | 案R2 ホスト別結果のインライン化 | 1ステップ5行→1行。ログと表記が揃う | 小 |
| 5 | 案R5 出力行のスタイル分け | 長い出力の構造が見える | 小〜中(正規表現分岐) |
| 6 | 案R3 凡例を初回のみ | 6回→2回 | 小 |
| 7 | 案R4 開始/終了の1行統合 | 1行/ステップ削減 | 小 |
| 8 | 案R7 `--tail-lines` | 大規模実行時のみ有効。既定オフ | 中 |
| 9 | 案R8 経過表示 | 無出力の長時間ステップの安心感 | 中(非TTY 分岐が必須) |

案R1・R6 が「見やすさ」の本質(**探す作業をなくす**)に効く。
案R2・R3・R4 は行数削減で、合計約21行/232行の圧縮。

## 補足: 未検証・注意点

- 案R6 の「マッチ件数・初出行」を `criteria.diagnose` が現在の実装のまま返せるかは**未確認**。
  項ごとの評価はしているが、内部で正規表現の match オブジェクトを保持しているかは要調査。
- 案R1 の表を追加した際、既存テスト([tests/test_cli.py](../tests/test_cli.py))が
  末尾出力を検証している場合は追従が必要。**影響範囲は未確認**。
- 実測は `COLUMNS=100` で行った。より狭い幅では最終集約マトリックスの
  ステップ名列が圧迫されるため、案R1 の表と同様に `overflow="fold"` の指定が要る。
- 案R8 は `soft_wrap=True` の設計意図と衝突するため、導入するなら非TTY 判定を必ず入れること。
